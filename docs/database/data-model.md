# Database model

## Conventions

- PostgreSQL is the source of truth.
- Primary keys use UUIDs generated by PostgreSQL.
- All timestamps use `TIMESTAMPTZ`.
- Foreign keys use explicit deletion policies.
- Status/type values are constrained with CHECK constraints in the initial schema. This avoids prematurely coupling application releases to PostgreSQL enum migrations.
- Flyway owns schema evolution. Do not edit an already-applied migration; add a new migration instead.

## Main relationships

- A subject has many conversations and one configuration row.
- A conversation belongs to exactly one subject and has ordered messages.
- A knowledge item is either global or owned by exactly one subject.
- A subject-owned knowledge item may be explicitly shared with other subjects.
- A knowledge item has immutable versions and one or more provenance records.
- A proposal belongs to a conversation and subject; approval creates or updates canonical knowledge.
- User documents have extracted chunks. Documents are not personal knowledge automatically.
- Research sessions belong to conversations and contain external source references.
- Audit events and outbox events support traceability and reliable asynchronous processing.

## Tables

| Table | Purpose |
|---|---|
| `subjects` | User-defined areas such as Programming, JDR or Sport |
| `subject_settings` | Retrieval, web research and model preferences for a subject |
| `conversations` | Conversation identity and owning subject |
| `messages` | Ordered user, assistant, system and tool messages |
| `knowledge` | Current canonical personal knowledge |
| `knowledge_versions` | Immutable snapshots of knowledge changes |
| `knowledge_sources` | User-originated provenance for knowledge |
| `knowledge_subject_access` | Explicit cross-subject sharing grants |
| `knowledge_proposals` | Pending candidates awaiting user approval |
| `documents` | Uploaded user documents and storage metadata |
| `document_chunks` | Extracted searchable text from documents |
| `research_sessions` | External research operations linked to conversations |
| `research_sources` | URLs, metadata and excerpts returned by research |
| `audit_events` | Important actions and state changes |
| `outbox_events` | Transactional queue for asynchronous work |

## Knowledge scope and access

`knowledge.scope` has two values:

- `GLOBAL`: `owner_subject_id` must be NULL; available in every subject.
- `SUBJECT`: `owner_subject_id` must be set; available to its owner and subjects listed in `knowledge_subject_access`.

Global knowledge must not have sharing rows. A subject must not share its knowledge with itself. These cross-table rules are enforced in the application service initially and should also be protected with database triggers or carefully designed database constraints if writes can bypass that service.

The backend computes the effective subject from the authenticated conversation. It must never accept a model-supplied subject identifier as authority for retrieval.

## Provenance

A knowledge source must point to exactly one user-originated source:
- a user message, or
- a user-uploaded document.

AI may summarize or normalize the content, but the source record must preserve traceability to the original user material. External web sources are recorded under research tables and are not valid knowledge provenance by default.

## Lifecycle

- **Archive**: hide from normal retrieval while retaining history and provenance.
- **Update/correction**: append a new immutable version; do not overwrite old snapshots.
- **Delete**: a separate, deliberate operation with explicit handling of dependent records and applicable retention requirements.

Conversation history is independent from knowledge. Deleting a conversation should not silently delete approved knowledge derived from it.

## Message mode

The selected input mode (`CHAT` or `COMMAND`) belongs to each message submission. It is not a conversation-wide setting. The initial schema stores it on the message so that the interaction can be audited and replayed accurately.

## Indexing

The relational knowledge and document text remain usable without vector indexing. Embeddings are derived data and will be added in a later migration after the embedding model and vector dimensions are selected. Failed indexing must never invalidate an approved knowledge write.

## Initial migration notes

The initial migration deliberately does not:
- create database users or authentication tables (authentication design is a separate concern);
- install pgvector or choose embedding dimensions;
- store full copies of arbitrary web pages;
- make uploaded documents automatically become knowledge;
- implement physical deletion workflows.

See `V1__initial_schema.sql` for the executable baseline.
